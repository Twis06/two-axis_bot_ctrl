The mechanism behind the 0.0% *median*: the frozen estimator's data gates (2-count stationary 250 ms dwells, 30 aggregates, span and conditioning) are rarely met during the registered calibration dwells, so it usually becomes usable late or not at all. *Corrected after review (I5): the correction is not "never active" when scored.*

- **Active during scoring in 22 of 50 runs:** those runs have a nonzero usable share within the scored dwells (mean 24%, maximum 100%).
- **When it is active, it helps:** 20 of 50 pairs improve, and 8 improve by 42–79%. These are load (0, 0.10) at both limits with seeds 102–104, and (0.06, 0.14) at 3.2 A with seeds 102 and 104.
- **When is it usable?** The "first usable median 16.6 s" is over the 37 ever-usable runs only.

This pattern (a large benefit whenever the correction is available, none otherwise) matters for the L5 "Conditional" outcome. The registered gate is still failed, on the median and on availability. It is a candidate design failure, not evidence that load learning cannot help: the known-load oracle reaches 76.9–78.6%.

## Independent review round 1: PASS WITH ISSUES (resolved)

| # | Finding | Resolution |
|---|---|---|
| I1 | Registered grids not checked; duplicate rows silently collapsed | `adoption_gate(..., expected_keys, expected_challenge_keys)`: a missing, unpaired or duplicate cell gives `incomplete`. Tests A and E. |
| I2 | Vacuous passes via "ordinary feasible" and scoring | Every registered pair must be scored (NaN → `incomplete`). "Ordinary feasible" = every registered held-out pair, independent of either controller's outcome. Tests B, C and G. |
| I3 | Target-current criterion could not fail | Replaced by the pre-clamp command `i_raw` against the active limit, with a 20 ms grace after a limit change. The applied target is kept as simulator consistency. Test on synthetic logs. |
| I4 | Challenge evidence from uncommitted sources, not rebuildable | Re-run and published from committed code (R4, `7366427` → `dff8efd`); the manifests record `est_seed`. |
| I5 | Overclaim "essentially never active" | Corrected (above): 22/50 runs active while scored, 20/50 pairs improve, 8 by 42–79%; first-usable median over 37 runs. |
| I6 | Lockout from truncated events; slower completion credited; missing telemetry = 0 | Lockout is read from its field. Completion later by more than 0.05 s is not credited. Missing learning telemetry gives `None` → `incomplete`. Tests D, F and H. |
| M1 | Onsets precede first usability | Late-onset amendment registered and run (above). |
| M2 | "2 of 6" wording | Corrected. |
| M3 | Payload-change feasibility | Wording corrected: a harness-level patch is possible but was not built. |
| M4 | "No correction while unusable" is close to self-consistency | Declared: `correction()` returns 0 when unusable. Bumpless transfer into the integrator on disable is not captured by this metric. |
| M5 | Availability applied more strictly than registered | Declared: the registration made <80% "conditional"; the gate records it as `fail`. The verdict does not depend on it (benefit fails too). |
| M6 | Attribution / provenance | `learn_ff` telemetry landed in `bdc46d1`; `exp/task3_gate.py` is now in the L4 provenance set. |

## Limitations

- **Missing challenge:** payload change was not executed.
- **Thin coverage of the active correction:** it is exercised in half the challenge runs, and the late onset leaves 1.5–4.5 s of scored motion.
- **Stale results checked indirectly:** "stale-result application" is checked as "no correction while unusable"; the L1/L2 tests cover late-worker rejection.
- **Assumed thresholds:** the gate thresholds (10%, 80%, 20%) are registered project thresholds. The progress slack (0.01), time slack (0.05 s) and limit grace (20 ms) are declared implementation choices.
